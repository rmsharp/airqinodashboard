# Framework Learnings

The methodology's own framework learnings, recorded as the canonical repo dogfoods itself. This
file is the companion to [`SESSION_RUNNER.md`](SESSION_RUNNER.md) — Phase 3C routes every session
to the right learnings home, and for a framework-level learning that home is here.

**Canonical methodology repo:** append a new row at Phase 3C — **append only; never renumber.** A
row's NUMBER is fixed forever, because every `Learning #N` citation resolves by number. Its CONTENT
may be **compacted** — said shorter without saying less, keeping every mechanism, figure and
citation. That is the one edit an existing row permits. The rows below are real framework learnings,
not placeholders.

**Budget the row before writing it — 1,500 B, checked by `bin/check-learnings`.** A partial read of
this table returns whole rows, because a row is one physical line, so row size is what a session
actually spends here: measured over 80 transcripts of the canonical repo, this file was read whole
once and read in part 243 times. **The check covers every row, not only the one you are writing** —
an over-budget row is a finding with a remedy, not a permanent red mark. Say it shorter rather than
raising the budget.

> **`#14` is reserved, and the gap between 13 and 15 is deliberate — do not close it by renumbering.**
> It is held by `docs/operator-gated-review-plan`'s D3, a branch from the *upstream* session sequence
> that is not present in every clone. S34 verified the reservation is attributable and respected it;
> S35 appended at **15** for the same reason. Renumbering would break every existing `Learning #N`
> citation, which is exactly what "append only, never renumber" exists to prevent.

**Adopter projects:** do **not** edit this file. Like `SESSION_RUNNER.md` it is synced from
canonical and must stay byte-identical, or local edits will block future syncs (see
[`BOOTSTRAP.md`](BOOTSTRAP.md), "Customizations Go in CLAUDE.md, Not in Synced Files"). Record
project learnings in your `CLAUDE.md` → **Project-Specific Methodology Adaptations** →
**Project-specific Learnings** subsection instead.

| 1 | Plan-mode output is a draft, not a verified plan. When a prompt contains a multi-phase plan with "implement," the deliverable is a plan document with evidence-based inventory, not Phase 1 code. The gap: Phase 1's task mapping had no entry for plan-mode handoffs, so the session defaulted to "implement." | 2 | **Protocol discipline is perishable.** 14 consecutive clean sessions can collapse to 1/10 deliveries within 12 hours of relaxed discipline. The protocol is perishable — it doesn't maintain itself. Each session must actively re-internalize it, not assume it's "already known." The compounding loop works only when every link in the chain is complete. | Field observation | Whenever you catch yourself thinking "I know the protocol, I don't need to re-read it" — re-read it. The fast-collapse case (FM #17 slow-drip's sibling) is real. |
| 3 | Plans should flag "here be dragons" areas where implementation is non-obvious — not all phases are equally risky. Call out which phases need extra caution, what assumptions are load-bearing, and where the executor should stop and re-orient. | Field observation | When writing any multi-phase plan. A plan that presents all phases as equally tractable lies to the executor about where the cost actually lives. |
| 4 | **Verify a plan's output against its completion criteria — not against session duration or count.** Execution speed is not evidence of plan quality, and "fits in one session" is not a planning goal. A plan whose phases each fit cleanly in one session and produce work that matches the completion criteria is high-quality; a plan that tempts the executor to bundle phases or skip close-out to "finish faster" is not. The "1 and done" rule does not bend for high-quality plans. | Field observation (refined from rmsharp feedback on issue #7) | When evaluating a plan or judging plan quality. Resist the temptation to read execution speed as plan quality — they are uncorrelated when the protocol holds. |
| 5 | Code review is a distinct deliverable, not overhead. Reviews that produce actionable plans (exact code snippets, line numbers, implementation order) have higher ROI than vague "this needs improvement" feedback. A review that doesn't identify specific changes a future session can execute is incomplete. | Field observation | When the session deliverable is a code review. Output an actionable plan, not a critique. |
| 6 | A plan written from memory of a file read is an assumption-level claim. Reading implementations before estimating complexity catches wrong assumptions early — estimating from a backlog description alone is unreliable. This is a special case of FM #11 (gaps from memory) and FM #20 (edit from memory) applied to planning. | Field observation | Before estimating effort or scope for any phase, read the actual implementation file. The backlog description is a hint, not a spec. |
| 7 | **Cross-reference completeness at self-review.** When a change adds a citation, an index entry, a glossary term, or any cross-reference between files — and especially when it modifies a numbered set (FMs, principles, phases, anti-patterns, learnings) — `git diff` confirms only the present-side edit; the defect is the *absence* on the destination side, which the diff cannot surface. Grep each cited destination to confirm the citation resolves, and grep nearby prose for set-size or named-membership assertions ("N failure modes", "the three workstreams") that may have drifted. Bidirectional: a new index entry needs its destination to cite back; a grown numbered set needs its size claims re-counted. | Three v2.6 instances: stale "24 failure modes" count, understated `/diagnose` + `/grill-with-docs` citation rows, aspirational `/init` citation (issue #19) | When a change touches any cross-file citation, index, glossary term, or numbered set. At self-review, grep destinations and size claims before committing — do not rely on `git diff` alone. |
| 8 | **A close-out gate is only as strong as the weakest checklist that summarizes close-out.** Session-type procedures (Planning, Review/Audit, Debugging, the vertical-slice revert, and campaign per-session checklists) each restate the close-out in condensed form. An agent following a condensed checklist never re-reads the full phase, so any cross-cutting gate the summary omits is silently exempted for that session type — exactly how an "authoritative" ledger acquires holes. When you add or change a close-out step, reconcile it into *every* checklist that restates close-out, not only the canonical Phase 3/Phase 6 text. This is Learning #7 applied to procedure summaries rather than citations. | FM #27 / escape #8 (CHANGELOG-ledger campaign, S7) | When adding or modifying any close-out or other cross-cutting gate: grep every session-type and campaign checklist that restates close-out and confirm the new step appears in each. |
| 9 | **A handoff is only dependable when it is a durable, machine-checkable artifact.** A transient narrative — spoken, or written only to the wholesale-overwritten `SESSION_NOTES.md` — leaves no evidence of its own absence, so a skipped close-out report is invisible until a human notices (the failure that motivated the receipt: an agent had to be *prompted* for its report). The fix mirrors the ledger (FM #27) exactly: **gate-on-write** (a `HANDOFFS.md` receipt whose structure `bin/check-handoff` verifies) **AND reconcile-on-read** (Phase 0 greps for a missing/`status: pending` receipt and backfills it `status: reconciled`) — neither is dependable alone. The honest ceiling is the same too: the check verifies presence and structure, never quality (a green check is not a good handoff), and a session that leaves no commit and no 1B stub still escapes. This is Learning #8 applied to the report itself, not just the ledger. | Close-out receipt slice (this session) | When adding any close-out artifact or gate: make it a durable, greppable artifact with a write-gate AND a reconcile-on-read backstop — never a transient note or a spoken summary. |
| 10 | **A review pass scoped to the diff has a blind spot: what the change made stale *outside* it.** Learning #7 (cross-reference completeness) and Learning #8 (close-out-gate propagation) are authoring-time self-checks — they catch drift the *author* introduces. But an adversarial review or audit is pointed at the diff by default, so "what did this change make stale elsewhere in the corpus?" is nobody's job. The v3.3 close-out-receipt work (#52/#53) shipped a clean 6-lens adversarial review, yet left `HOW_TO_USE.md`, the `README.md` repo tree, and three tutorials describing close-out *without* the new receipt — none were in the diff, so no diff-scoped lens looked at them. A human had to ask "has documentation been fully updated?" (fixed in #54). | Upstream issue #55 (completeness-critic proposal), motivated by the v3.3 doc-completeness gap fixed in PR #54 | Promote Learning #7/#8 from an authoring self-check to a review-time lens: when a change adds, renames, or removes a concept, artifact, file, step, or numbered-set member, grep the *whole corpus* (not just the diff) for file/artifact enumerations, worked examples/tutorials, indexes/cross-references, and count/size claims ("N failure modes", "the six requirements") that now lag. See `workstreams/AUDIT_WORKSTREAM.md`'s Verification Checklist for the operative step. |
| 11 | **Heterogeneous capability tiers within one slice are a division of labor, not a new gate.** Splitting a pre-declared vertical slice's layers across agents of different capability tiers — with the strongest tier reviewing every lighter-tier layer's output before that layer's checkpoint commit lands — satisfies the existing per-boundary verification gates (c)/(d); it does not add a fifth gate or substitute for the build/test matrix. The risk is a plausible-sounding misreading: treating cross-tier review as proof a layer is correct on its own, or batching review to the end of the slice instead of per boundary — either one reopens failure mode #26 (mega-session masquerading as a vertical slice) wearing a division-of-labor costume. | The close-out-receipt slice's own hybrid capability-tier build (`HANDOFFS.md` session S1; concrete agent/model names live in `RECOMMENDED_SKILLS.md`), formalized as the §Vertical Slice Sessions "capability-tiered review" addition (BL-7) | When a slice's layers will be built or reviewed by agents of different capability tiers: state the tier assignment in the gate (a) contract, delegate a layer only where an objective gate (test suite, exhaustive grep, mechanical spec) proves its correctness, and confirm review happens per boundary before each checkpoint commit — never as one pass at the end. |
| 12 | **When an invariant is mechanical, encode it as a test — a review-time grep is a human step that silently stops happening.** #7/#10 are that grep: apt for prose relations, weak between two enumerable sets. v3.3 added `HANDOFFS.md` to the distributed corpus, not the health scanner's methodology checklist, which silently stopped describing the corpus it scores, for *two* releases of those greps. As two lists ("every distributed adopter-root destination is on the checklist or explicitly exempt with a stated reason") it is a few lines of test, plus one guarding the guard: a stale exemption naming no real file hollows the invariant. So the class closes: the next such file fails the suite instead of going uncounted. Non-negotiable: drive it RED on unpatched code; watch it fail before trusting it. A mechanized invariant never seen to fail is that trap one level up, hit twice: an absence-check filtered a dict by `"Large files" in r`: keys, vacuous pass; a fixture whose render toolchain short-circuited the counts under test could not fail, yet looked like coverage. | Dashboard signal-integrity campaign (S9–S16): manifest-vs-checklist guard S9 → Layer 1; 2 vacuous tests, Layer 7 | When something joins an enumerable distributed set, or you lean on #7/#10 to align two lists: assert the relation, RED first. Pair every absence assertion with a presence control; ask what a fixture makes *unreachable*, not just what it asserts. |
| 13 | **A forward-looking claim cannot be checked by re-reading a file — it must be computed.** Learning #6 and FM #11 catch claims written *from memory*; both prescribe the same repair: re-read the confirming file. #7, #10 and #12 catch cross-refs gone stale *in the corpus*. Neither reaches a handoff's predictions. "Expect one merge conflict", "these are the files you will touch", "this should be quick" describe a state that does not exist yet, so no file confirms them; the only honest check is to derive it or call it a guess. The Source case did not go stale — the tempting diagnosis, and wrong: it was never true. A wrong prediction is worse than none: it licenses the successor to resolve *quickly*, not *carefully*, and a merge resolved on the belief that "only the ledger differs" discards work silently, with no failing check to catch it. | This repo's v3.6 release — a receipt predicted one conflicting file and the merge met seven; the sentence was written in a commit that had itself changed all seven | When you *write* a forward-looking claim — a merge outcome, the files the next session will touch, an effort estimate — derive it or label it a guess. For a merge, deriving is exact and touches no working tree: `git merge-tree --write-tree --name-only <ours> <theirs>` lists conflicting paths between line 1's tree id and the trailing `CONFLICT` block. When you *inherit* a prediction, re-derive it before acting. |
| 15 | **Prove "nothing lost" over the PARTITION, not the total: a whole-set check is structurally blind to misplacement.** Across two artifacts (ledger/archive, file/extraction, table/sibling), *reassemble, compare to the original* is necessary, never sufficient: **moving content between halves is exactly preserving under reassembly**. Here a byte-for-byte whole-file `md5` reconstruction shipped in the same commit that moved a file-scoped paragraph out of its declaring file: still *somewhere*, so it passed; still missing. Newest-on-top puts such text at the bottom, where an oldest-first cut takes, migrating *by position* unless pinned. **Repair:** zone *before splitting* (partitionable vs. file-scoped), assert each separately (*every byte of the pinned zones is in THIS file, absent from the other*), alongside reassembly, never instead; scope it to the partitionable zone only, or any legitimate regeneration trips it: refuses every run. **Publish the payload BOUNDARY and COMMAND with any digest:** a hash whose payload definition is unrecorded cannot be re-derived by a successor (five reconstruction attempts here failed): assertion, not proof. | S35 (2026-08-03), ledger-trimmer design: 3 hand-run archives, one lost content while its proof passed | Any split, extraction, archive, migration or de-dup moving records between artifacts. The tell: a check on totals (counts, sizes, digests, "N in, N out") not where each part landed. |
| 16 | **Wire the assertion to the ARTIFACT, not the inputs it came from; a predicate-only mutation score proves nothing.** Learning #12 (encode the invariant, drive it RED) can pass with an inert guard: it asks if the assertion *is correct*, never *what it is handed*. Operands derived from each other assert an identity: `records[:k] ++ records[k:] == records` holds for every input, so the guard cannot fail however badly the code between split and write corrupts it. Tell: operands computed, not read back. **Repair: re-parse what you will write with the grammar you will read it with and assert over THAT.** Mutation harnesses inherit the blind spot: killing every predicate mutant proves them correct *as functions*, not wired to anything. Mutate the **producer** (the code that builds the artifact), not only the **checker**; checker-only mutation scores 100% over tautologies. | S36 (2026-08-03), ledger trimmer: a 13-mutant harness killed 13/13 while all 3 losslessness assertions were identities at their only call site; a write path silently dropping a record printed `[L1_OK] [L2_OK] [L3_OK]`; only the independently generated proof script caught it | When checker and checked share a run: losslessness proofs, round-trip/idempotence, reconciliation, migration verifiers, transform invariants. Ask *where did each operand come from?* (one source for both = identity) and *does my mutation set include the producer, or only the checker?* |
| 17 | **A spec demanding both "read X's value" and "assert yours equals X's" is a contradiction, not two requirements; the owed test's falsifiability picks the half to build.** A **ratified** design put both **in one paragraph** — read the owning tool's number; prove the displayed number *equals* it — yet still read as two. Read the first literally and the second is an identity over one value: passes forever, cannot fail, certifies nothing — #16 one level up: tautology in the **spec**, not a test. Don't read harder or pick a favourite: **build the reading whose owed test can go red** — compute independently, reading only the one input that tool owns (a calibrated constant, regex-parsed from source). Force disagreement to prove it discriminates: three separate divergences did, each a real defect the agreement would have hidden. **Corollary (load-bearing):** an agreement holding only by this repo's history isn't one: every archive shard here shrank its ledger, so a missing filter agreed by luck; only a fixture built to break it diverged. Ask what accident of *this* corpus holds them together; build the case removing it. | S38 (2026-08-03), trim-trigger dashboard row: design §1.3 asked for both; agreement test broke the tie | A design that consumes another component's value AND must show they agree: dashboards over tools, caches over sources, denormalised fields over origins, re-implementations synced to a reference. |
| 18 | **Instructional prose asserts behaviour: RUN the artifact, name the command whose output you watched; "the design says so" cites an intention, not a behaviour.** Learning #16 (test wired to the artifact, not its inputs) has a prose sibling that bites harder: no red state to fail into. A ratified design promised *"staged-but-uncommitted"*; the tool never stages. In a distributed template it would have told every adopter their change was staged, so an ordinary `git commit -a` would land the shortened ledger, never its removed-records archive: exactly the loss its three losslessness assertions exist to prevent, invited by documentation, not code. The spec was stale, not lying: its rollback table two lines below already contradicted it. Same session, second instance, same file: a repo-history anecdote's causal order inverted from two same-day timestamps; `git merge-base --is-ancestor` settled it. | S40 (2026-08-04) ledger-doctrine seeds: `--write`'s seed copied "leaves the change staged for you" verbatim from `ledger-trimmer-design.md:722`; shipped tool: no `git add` anywhere, prints `WRITTEN (uncommitted — this tool never commits)`, shard untracked | Before shipping any behavioural sentence in a spec, seed, or distributed template (what a tool leaves staged, tracked, committed, or otherwise does), run the artifact and watch what it actually does. Causal order (*this before that*): one command, not inferred timestamps. |
| 19 | **A version tripwire keyed to something that never changes across versions cannot fire — and it fails by reporting *current*, worse than silence.** A stale-format detector matched each adopter-owned template against a marker string, its H1 title. Stable — why it was chosen — but stability is half a version marker; the other half is **absence from the versions it must detect**, and a title that never changed is absent from nothing. So when the format did change, every old-format project matched and read **current** — a confident wrong answer — while a promise elsewhere in the corpus ("the format lag is surfaced rather than silent") went false, no test failing. It is the unkillable guard in *data*: a key no version change can falsify is a constant shaped like a version check. Accept that upkeep rather than design around it — a discriminating marker must MOVE whenever the format materially changes, pin it with a case that reddens when it hasn't. | S41 (2026-08-04), the URL-update-path fix: `SEED_FORMAT_MARKERS` keyed each distributed seed's check on its own H1 title; 11 siblings holding `CHANGELOG.md` and 9 holding `HANDOFFS.md`, none carrying the new doctrine, all reported `present` | Designing or reviewing any version/format/staleness tripwire: name a past version the marker would actually have caught. If you cannot, it is decorative — re-key on something provably absent from the versions it must detect. |
| 20 | **Reviewing candidates independently does not review their SYNTHESIS: a graft of reviewed pieces is itself unreviewed.** The panel was sound (fresh agents, no shared state, one lens each) and its judges did verify their candidate against the real source, not trust its prose — but each *alone*: nobody scored the seam where two candidates' pieces meet, and a defect there is unreachable from either alone, in which those pieces never coexisted. **The tell: ask what the judges scored.** If it was "each candidate as written" *and* the shipped design matches no single candidate, judging has zero coverage of what ships. Repair: an independent pass over the **synthesis**, not a re-score of candidates, ideally shaped unlike the process that produced it and missed the seam: hand-trace, citation re-check. | S57 (2026-08-09), issue #67 fix plan: a 3-candidate/6-judge panel scored each candidate in isolation; the synthesis grafted one candidate's target-scoping onto another's `.gitignore`-aware gate; a second adversarial pass found a HIGH-severity graft defect: the gate silently went unconditional whenever target-scoping pointed at a directory not yet a git repo — invisible to any review of either candidate alone | When a design, plan, or fix grafts (not merely selects) pieces from independently-reviewed candidates, proposals, or PRs: review the combined artifact afresh — judge scores cover the ingredients, never the recipe. |
| 21 | **"Make it shorter" is met by moving a size-CORRELATED metric while the target stays flat, and an adversarial verifier correctly built for lost facts cannot flag a candidate that dropped nothing and shortened nothing real: lossless ≠ compacted.** Told "~40-60% of the original line count" (symptom: line cap), every candidate unwrapped hand-wrapped breaks into one paragraph: 27 lines to 3, chars down 0.0-0.6% on most receipts (one 2,458 to 2,457); 150 agents' work passed every check achieving almost nothing. A direct character count, not trust in "fewer lines", caught it pre-commit; the real constraint was a BYTE budget. **Ask which unit the downstream problem is measured in; instruct, measure and verify in THAT unit, not a proxy; where fewer lines meet the letter without moving what the consumer reads (bytes, distinct facts, tokens), ban reformat-only edits.** | S61 (2026-08-09), `HANDOFFS.md` trim: 39-receipt compact+verify Workflow pass, line-count target: ~1.4% real (character) reduction reported apparent success (fewer lines, zero verify failures on the reduction dimension); re-run on an explicit character target + "line-unwrapping isn't compaction": real reduction 4.7% | Any agent/workflow asked to make an artifact smaller/shorter/more compact, checked only for correctness/losslessness, never target-metric movement: compaction, summarization, log-trims, prose edits, boilerplate cuts; count that unit both sides. |
| 22 | **A completed item's own TEXT can be load-bearing for a sibling's meaning: deleting it silently orphans a reference; no test catches it.** Phase 3F's "remove a completed backlog item in the same commit" assumes independent deletability. | 23 | **A backlog/issue item naming a defect is a claim frozen at filing time, not a live read of current behavior — unrelated work between filing and actioning obsoletes it, record unrevised.** `church_growth/BACKLOG.md` flagged `detect_doc_only()`'s self-referential source-LOC miscount (2026-07-21) as needing a canonical-repo fix; another campaign's four commits shipped it four days on (Layer 7, `ae9e5b7` et al., 2026-07-25). | 24 | **A check keyed to the LIVE file has a population the protocol's own archiving moves out from under it; empty reads "failed", not "nothing to check".** FM #28 ceilings every mandated-read artifact, exceeding it a defect, so archiving is routine: a whole class of checks turns conditional on where its population lives. `bin/tests.sh` Test 29 body-line-budgets `CHANGELOG.md`'s `Reconcile-on-read` entries, pass `count > 0 && violations == 0`. An operator-directed trim moved the last 10 to a shard: count 0, `budget violated -- `, nothing after the dash. | 25 | **A correlation perfect across every artifact you have can be a confound: collinear causes separate only at the off-diagonal cell.** Six proof scripts split by generator version (old fail, new pass) and identically by whether its commit bundled edits beyond the proved one: two variables, one population, none separating them. The filing disclaimed causation, blamed the version anyway: six artifacts make a perfect split look total. Build the missing cell, usually far cheaper than the reasoning it replaces: two swaps, two runs (new script, old artifact; then reverse) inverted it: new failed all four old cases byte-identically, old passed new. It had fixed a real, different second defect, hence the clean split; regenerating provably fails, effort wasted unnoticed. A failing proof is evidence about the proof, not the data: re-running repeats it, regenerating greens unexamined content. Re-derive by other machinery (identity, not position), mutation-proved able to fail before trusting its zero (Learning #16). | S88 (2026-08-15), auditing four archive losslessness proofs FAIL five days: archives intact, same-commit bundling broke their positional identity, every generator version | A report blames a correlated cause (version, flag, directory, author, date): what else splits your actual population identically? Never argue it out: copy the check, swap in the other case, run it; re-derive a failing check by unshared machinery. |
| 26 | **Archiving everything FINISHED can still leave a file over its ceiling: the excess may be the LIVE work, which no reduction can remove.** A backlog ran 2.10x its own ledgers' budget; the agreed diagnosis was true: 45,288 B in 11 closed items sat in the open-work-only section, unremoved at close-out against Phase 3F. Archiving all of it verbatim recovered 33%, correct and worth doing, yet missed the ceiling — unreachable by it or any housekeeping: measured before the session's own writes, the OPEN items alone were 1.04x the budget. The tell precedes the work and costs one measurement: **sum the part you may NOT remove and compare that to the ceiling first.** If that remainder exceeds it, ship the reduction plus that finding, not the ceiling; the real question is policy (how much live work may this file hold?) that no amount of archiving can answer. Also: no file can accurately state its own byte size (writing it in changes it); keep it elsewhere with a re-derivation command. | S89 (2026-08-15), `docs/planning/BACKLOG.md`, after FM #28 was measured to cost a session: 137,440 -> 91,857 B (-33.2%), all 11 archived, still 1.40x the 65,536 B yardstick; 16 inherited open items: 68,195 B | Handed a size target for a grow-and-must-be-read artifact: before agreeing it is reachable, sum what you may not touch and compare to the ceiling; if that alone exceeds it, re-scope at claim time to reduction plus finding, not close-out |
| 27 | **A derived number and its goodness-of-fit statistic are TWO claims, only the first read: the number carries authority, the caveat is scenery.** A tool emitted `opening_tokens ≈ 46,319 + 0.0692 × bytes, R² = 0.0513 ⇒ 14.45 B/token` — both tells on screen: R² 0.05 = 5% of variance explained; 14.45 B/token is implausible on its face for dense markdown.
